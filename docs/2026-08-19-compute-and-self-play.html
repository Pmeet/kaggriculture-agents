Would a compute farm get us to the top?

Short answer: the box is cheap and easy, the serverless platforms are the wrong shape, and neither matters much — because compute is not what is currently limiting us. Self-play against our own agents has a ceiling we have already hit, and we can measure exactly where it sits.

Part 1

Which platforms actually work

This one is straightforward, and the answer splits cleanly. Our workload is CPU-bound batch: a long-running process pegging every core for hours, no network, no requests. Serverless platforms are built for the opposite — short, I/O-bound, request-triggered work.

Fit for a long-running simulation batch.
OptionVerdictWhy
Cloudflare WorkersNo Per-request CPU caps and no persistent process. It's an edge runtime for request handling; Python support runs through Pyodide and is far slower than native. Sustained batch compute also runs against the free-tier terms.
Vercel FunctionsNo Same shape. Hard per-invocation duration limits, no multi-core batch, and the free tier explicitly isn't a compute farm. You'd spend the effort fighting the platform.
Docker on a small VMYes Exactly right. A plain container, a cron entry, a volume for results. Oracle Cloud's always-free ARM instance is the generous option; a small Hetzner box is a few euros a month and simpler.
GitHub ActionsPartly Free minutes on public repos, 2-core runners, 6-hour job cap. Fine for a nightly regression run, poor for continuous search — and this repo is private, where minutes are metered.

Throughput, measured rather than guessed: this machine does 3.2 games per second on 16 workers. A 4-core free VM would manage roughly a quarter of that — call it 70,000 games a day, every day, for about the price of a coffee. That part of your idea is entirely sound.

Part 2

The three claims underneath the question

More games make the tuning bettertrue, low ceiling

Real, but it is the avenue that has paid least. lab/evolve.py already runs a joint evolutionary search across all 86 tunable parameters, with held-out validation built in. More compute would let it search longer.

Weigh that against what actually moved the needle today. Four parameter sweeps — walking cost, same-tile chaining, pen price, animal cutoff — returned noise or negative. The two real wins were bugs: livestock bought and never delivered (+$28.7k) and harvest withheld until max yield (+$3.7k). Neither was findable by search, because every agent we own had them.

Playing thousands of agents we built approaches perfectionfalse, and measured

This is the load-bearing claim, and it's where the plan breaks. Self-play explores only the strategy space your parameterisation spans. Our agent is 2,373 lines of hand-written heuristics with 86 knobs. Search can turn the knobs; it cannot invent a strategy the code has no way to express.

We have already run this experiment. The local gauntlet reads MEAN 1.000 / WORST 1.000 — we beat every opponent we have ever built, decisively — while the same agent was scoring about 0.46 on the ladder. Generating a thousand more of ourselves moves the first number not at all and the second not at all.

The AlphaZero intuition is the right reference, but it breaks on one detail: AlphaZero's strategy space is the network, so self-play can discover genuinely new play. Ours is a fixed program. Self-play optimises within it and converges to the best version of the farm we already know how to describe.

Improvement compounds even against the wrong opponenthalf true

This is the strongest part of your argument and it does hold — for one class of improvement. Split them:

  • Opponent-independent — bug fixes, wasted actions, unsold stock, an animal that never reaches its pen. These transfer to any opponent, and self-play can surface them if the measurement is right.
  • Opponent-dependent — market timing, what to grow, when to undercut. These are fitted to whoever you played. Tuned against ourselves, they encode our own blind spots and can be actively wrong on the ladder.

Most of the remaining gap is the second kind. The top agents beat us on the crop economy — a different farm, not a better-tuned version of ours.

Part 3

What I would build, in this order

  1. Real opponents in the poolunblocks everything

    Reconstruct two or three top ladder agents from replays as playable opponents. This is already an open lead in the handoff and it is the single highest-value item, because every compute-hungry idea below produces a misleading answer until it exists. Cheap in compute, expensive in thought — which is exactly why it hasn't happened yet.

  2. A nightly ladder postmortemcompute helps

    Pull our real ladder games each night, run lab/postmortem.py over them, and write a report into the repo: which games we lost, what they had in common, whether the engine version changed. Modest compute, and it uses the one opponent set that is unarguably real. It would also have caught both silent engine changes on the day they landed.

  3. Large-sample failure characterisationcompute helps

    Thousands of self-play games, not to count wins but to characterise the losing tail. Our objective is Pr[win] = Φ(μ/σ), and shrinking σ needs hundreds of losses to study, not five. This is your original instinct and it is correct — it's the one use where volume genuinely buys understanding.

  4. Longer parameter searchlowest ceiling

    Let evolve.py run overnight against the improved pool. Worth doing once items 1–3 exist. Worth little before them, because it would be optimising against a saturated benchmark with more decimal places.

The honest risk

Six weeks, and infrastructure is not the deliverable

The deadline is 30 September. Building and babysitting a cloud pipeline is a days-long project that produces no agent improvement by itself. Everything that has actually moved our rating this season came from reading a replay or an engine source file and noticing something wrong — hypothesis generation, not evaluation throughput.

So the recommendation is a small version of this, not the full farm: one cheap always-on box running the nightly ladder postmortem and a weekly evolve pass, writing reports into the repo for review. That captures most of the value for a fraction of the effort, and it keeps a human — or an agent reading the report — in the loop, because every trap that has cost us time this season was conceptual rather than statistical. A faster wrong measurement is still wrong.
